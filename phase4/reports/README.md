# Phase 4 Repository Validation Reporting Standards

This directory contains evaluation reports and audit scorecards generated from auditing real-world repositories with SentinelPR.

---

## 1. Mandatory Report Structure

Every repository evaluation report must follow a standardized structure and document:

1. **Repository Metadata:** Name, owner, URL, branch, language, and primary framework.
2. **Pinned Commit SHA:** Exact 40-character commit analyzed.
3. **SentinelPR Version:** Released artifact (`v1.1.4`) or development commit hash.
4. **Rules Evaluated:** Complete list of active security and code-quality rules.
5. **Findings Detected:** Total findings generated by the engine.
6. **True Positives (`TP`):** Count of verified genuine flaws detected.
7. **False Positives (`FP`):** Count of verified safe code flagged incorrectly.
8. **False Negatives (`FN`):** Count of verified genuine flaws missed.
9. **True Negatives (`TN`):** Count of verified safe constructs correctly ignored.
10. **Uncertain (`UNCERTAIN`):** Count of findings with inconclusive ground truth.
11. **Detection Observations:** Detailed commentary on specific findings and patterns observed.
12. **Remediation Observations:** Success/failure rates of automated patching, patch syntax validity, and compilation rates on external classpaths.
13. **Operational Failures:** Engine exceptions, timeout events, JavaParser parse errors, or classpath resolution failures.
14. **Root Cause Analysis:** Technical explanation of parser limitations, taint tracking oversights, or framework mismatches.
15. **Actionable Engineering Follow-Up:** Concrete technical backlog tickets recommended for SentinelPR hardening.

---

## 2. Statistical & Metric Integrity Rules

> [!WARNING]
> **Strict Guardrails for Real-World Metrics:**
> 1. **No Speculative Percentages:** Do **NOT** publish overall "Precision", "Recall", or "F1-Score" on a repository unless the underlying ground truth for the entire codebase (including negative space) has been thoroughly audited and verified.
> 2. **Never Fold UNCERTAIN into TN/FP:** `UNCERTAIN` observations must remain tracked in their own category. Treating uncertain cases as true negatives or false positives introduces artificial bias and invalidates metrics.
> 3. **Distinguish Benchmark vs. Real-World:** Never describe controlled 108-case benchmark results as representative of real-world production performance. Real repositories test unexpected idioms and edge cases not covered by synthetic fixtures.

---

## 3. Storage Convention

Reports are persisted as markdown and JSON summary documents:

```text
phase4/reports/
  REAL-REPO-001-Todo-Application-report.md
  REAL-REPO-001-Todo-Application-report.json
```
