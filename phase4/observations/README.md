# Ground-Truth Classification Protocol

This guide defines the mandatory engineering process for reviewing, classifying, and verifying findings observed when auditing real-world repositories with SentinelPR.

---

## 1. Mandatory 10-Step Review Process

Every finding generated by SentinelPR during a repository audit must pass through the following 10-step protocol:

1. **Execute SentinelPR:** Run the engine against the target repository root in a controlled environment.
2. **Record Repository Commit SHA:** Pin and record the exact 40-character commit SHA of the audited repository.
3. **Record SentinelPR Build:** Record the exact SentinelPR release version (`v1.1.4`) or commit hash utilized.
4. **Preserve Raw Finding:** Archive the verbatim finding JSON object (rule, file, lines, confidence, raw snippet).
5. **Inspect Actual Source Code:** Review the source file in its full context, including imported types, base classes, annotations, and configuration properties.
6. **Determine Genuine Vulnerability:** Trace dataflow paths from entry points (controllers, handlers, consumers) through business services down to sinks. Determine whether the path is truly exploitable or safely mitigated.
7. **Document Ground-Truth Evidence:** Write down verifiable evidence citing specific lines, framework guarantees, or validation mechanisms.
8. **Assign Classification:** Classify into `TP`, `FP`, `FN`, `TN`, or `UNCERTAIN`.
9. **Handle Inconclusive Cases:** If evidence is ambiguous, incomplete, or dependent on unstated production environment configurations, classify strictly as `UNCERTAIN`.
10. **Preserve Repository Integrity:** **Never** modify the audited repository code merely to simplify or force a classification.

---

## 2. Classification Requirements

### True Positive (`TP`)
- **Condition:** SentinelPR reported a finding on a genuinely exploitable vulnerability.
- **Evidence Requirement:** Demonstrate the untrusted source, the path to the sensitive sink, and the lack of effective sanitization or framework-level protection.

### False Positive (`FP`)
- **Condition:** SentinelPR reported a finding on code that is verifiably safe.
- **Evidence Requirement:**
  - Clearly cite the specific defensive construct (e.g., ORM parameter binding, explicit allowlist validation, safe encoding, secure framework defaults).
  - Document the exact engine limitation (e.g., missed sanitizer pattern, AST false assumption, lack of framework context).

### False Negative (`FN`)
- **Condition:** A genuine vulnerability exists in the repository that SentinelPR failed to report.
- **Evidence Requirement:**
  - Trace the complete source-to-sink flow.
  - Document why SentinelPR missed it (e.g., unmodeled sink API, complex aliasing, cross-module gap, reflection).

### True Negative (`TN`)
- **Condition:** A security-sensitive construct was inspected, and SentinelPR correctly determined it to be safe and remained silent.
- **Evidence Requirement:** Reference the verified safe construct and confirm no erroneous finding was emitted.

### Uncertain (`UNCERTAIN`)
- **Condition:** Available static evidence is insufficient to prove safety or exploitability conclusively.
- **Evidence Requirement:**
  - Document the missing evidence required (e.g., external filter configuration, database schema constraints, deployment environment variable guarantees).
  - Do NOT count `UNCERTAIN` as a successful detection or as a safe pass.

## 3. Observation Records Storage

Individual repository observations are stored as JSON files conforming to [`finding-observation.schema.json`](../schemas/finding-observation.schema.json) under:

```text
phase4/observations/<repository-id>/
  OBS-0001-<rule-id>.json
  OBS-0002-<rule-id>.json
```
